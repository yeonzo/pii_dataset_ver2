## 적용 범위

`relation_document_pipeline`의 기본 설정에 `spec_policy: type_specs_v1`을 적용했다. 원본 Git 커밋 `deaa2f6403a22253c9ebc70fe9ead5563d5257bd`의 도메인·subtype별 형식 분리 방식을 참고했다. 원본 코드와 동일한 구현이라는 의미는 아니다.

6개 도메인의 78개 subtype 전체에 작성자·독자·당사자 역할, 전용 항목 순서와 표현 형식, 필수 사실, 상황별 포함·제외, 내용의 완성 기준을 정의했다. 총 314개 구간과 628개 필수 사실 필드다. 별도 `resume` 도메인은 제외했고, 사용 중인 `career_education/resume_form`은 포함한다.

구독 환불·상품 반품·예약 취소, 휴학·복학, 직무·학업 추천, 초진·재진은 명시적인 상황 선택을 지원한다. 나머지 타입은 각 타입의 조건별 규칙을 계획 단계에서 해당 사건에 맞게 확정한다.

원본 subtype별 분량 범위와 `max(1500, int(length_target * .75))` 하한, 원문을 보존한 추가 방식, 문서당 최대 7회 및 공유 재시도 1회 제한은 유지했다. 새 LLM 단계는 없다.

## 구체적으로 남은 문제

1. **형식을 요구해도 생성기가 실제 형식을 완성하지 않는다.** 용역 계약서에는 산출물과 일정 관련 정보는 있지만 요구한 헤더·행 구조의 표가 없다. 조정 신청서도 쟁점과 자료, 협의와 조정안의 표를 문장 나열로 작성했다.
2. **필수 사실을 짧고 일반적인 문장으로 채운다.** 추천서의 두 관찰 사례가 구체적인 과제·어려움·본인 행동·관찰 결과를 충분히 설명하지 않는다. 새 완성 기준이 이를 실제로 탈락시켰다.
3. **문서 역할이 수정 과정까지 일관되게 유지되지 않는다.** 용역 계약서에서 두 당사자가 번갈아 계약자·서비스 제공자·지급자로 쓰였다. 추천서는 추천인의 1인칭 관점과 피추천인·추천 목적이 불명확했다.
4. **사실 계획과 본문 사이의 수치·상태 일관성이 부족하다.** 본문을 직접 확인하면 환불 기록의 승인 대기와 승인 완료가 섞이고, 피해 신고의 총액 300만원과 열거한 150만원·100만원의 합계가 다르다. 이는 관찰된 본문 문제이며, 이 두 건의 최종 종료 코드는 분량 추가 실패다.
5. **추가 분량 생성이 요구량을 지키지 않는다.** 3건 모두 짧은 두 문장 수준을 반환해 유효한 추가 블록을 확보하지 못했다. 제목·사실 정의를 추가한 것만으로 이 문제가 해소되지는 않았다.

법률·계약 검수는 응답 자체의 증거 검증에 실패했다. 그 응답에 기록된 본문 문제와 `spec_checks`는 진단 참고 자료이며, 유효한 최종 검수 결과로 집계하지 않았다. 추천서는 유효한 검수 응답에서 새 타입 기준 미충족으로 탈락했다.

따라서 이번 변경은 **모든 타입의 작성·검수 계약을 실제 경로에 적용한 상태**이며, 실제 문서의 최종 품질 개선 성공을 입증한 상태는 아니다. 후속 개선 지점은 사실 계획의 사례 밀도, 수정 시 역할 보존, 실제 표 렌더링, 추가 블록의 내용량 준수다. 이번 결과를 통과시키기 위해 분량이나 품질 기준을 완화하지 않았다.
